# 安装与验证经验

## 为什么要构建合并目录

Codex 桌面端右下角模型菜单从它使用的目录读取模型。单纯在用户级 config.toml 增加 model_providers、model_catalog_url 或本地 model-catalogs 文件，不保证官方模型与第三方模型在同一个菜单出现，更不会自动给每个条目切换 Provider。此工具生成合并目录，并为新增模型明确指定 Provider。官方模型和认证路径继续保留。

## 连接信息和密钥

在连接 JSON 中只写 env_key 名称。连接内容的 id 必须以 local- 开头，base_url 一般以 /v1 结尾，wire_api 要与服务实际支持的协议一致。/v1/models 缺少 context_window 时，提供 model_specs。上下文长度是服务能力声明，不应从模型名称推测。若某模型实际只支持 Chat Completions，应配置 wire_api 为 chat_completions 并单独验证工具调用和指令兼容性。

Windows 的图形应用有时看不到启动终端临时设置的变量。本派生版在当前进程环境没有值时，可读取 Windows 用户级环境变量。把密钥保存为用户级持久化环境变量后，重启并登录仍可读取；首次设置后重新启动桌面端。不要把密钥放在连接文件、TOML、构建输出、命令行参数或公开 issue 中。

若用 Windows PowerShell 5.1 执行含中文的安装 `.ps1`，请将脚本保存为带 BOM 的 UTF-8。无 BOM 的文件可能被按本地代码页误读，导致 here-string 内的 Python 检查代码被当作 PowerShell 解析，出现 `from` 关键字不受支持等连锁报错；此类解析错误发生在脚本执行前。

## Windows 上的实际观察

### 中科大平台五模型接入验证

2026-10-23，用用户自己的 API Key 调用 `https://api.llm.ustc.edu.cn/v1/models`，返回 13 个授权模型 ID。从中选择 `deepseek-flash`、`glm-5.3-flash`、`qwen3.8-flash-next`、`qwen3.8-reasoner`、`deepseek-v4-flash`。逐个对 `/v1/responses` 发送短文本请求，五个都完成；再发送要求调用 `echo(value=42)` 的工具请求，五个都返回了 `function_call` 和正确参数。将 `max_output_tokens` 设为 32768 的短请求也均被接受；这仅验证请求预算参数可用，没有实际生成那么多 token。64 输出 token 对部分推理模型不够，曾出现 `incomplete`，增加到 512 后短请求完成。平台公告称 `deepseek-flash` 已升级至 DeepSeek-V4.1-Flash-1017，但调用 ID 不变；不要将此公告直接套用到 `deepseek-flash-2`。

无密钥配置见[示例](../examples/ustc-connections.example.json)。`model_specs` 的上下文长度采用平台公开部署信息中的 1M 或 262K 级别；网关部署或权限变化后应重新核对。连接使用 `env_key = USTC_API_KEY`，密钥值留在 Windows 用户级环境变量中，不进入仓库、目录或 TOML。实例构建保留 11 个官方目录条目、3 个原有 Claude 条目，再加入上述 5 个；针对当前签名桌面端的隔离验证通过。`/v1/models`、短文本和单次工具调用均不能保证复杂长任务的稳定性，应在实际菜单中继续验证。

Windows 安装器要求 Codex 桌面端正常退出。构建和隔离验证可以在客户端运行时完成；激活新目录与适配器服务时，需要退出客户端，再运行已验证构建的安装命令。这样也能保留原有官方模型的登录与路由。

2026-10-22 的本机试验使用 Codex 桌面版 26.1016.6573 和 CLI 0.163.0-alpha.11。构建结果合并了 10 个官方 GPT 条目和两个第三方条目 claude-sonnet-4-6、claude-opus-5-5。原生适配器的隔离验证通过；通过适配器发出的简单请求中，GPT 和 Sonnet 正常返回。Opus 请求收到服务端响应，但一次要求仅输出 42 的测试返回了无关搜索内容，因此只能说明链路可达，不能确认该服务端的 Opus 路由和行为可靠。

第三方服务的 /v1/models 在当时会拒绝 Python 默认 User-Agent，表现为 HTTP 1010。本派生版给发现和推理请求设置了明确的 User-Agent。此经验只说明这一服务的当时行为，并不保证其他服务兼容。

同日的增量检查中，服务目录列出了 claude-sonnet-5-5；其最小 Responses 请求正常返回 `42`。增量构建保留了 11 个官方目录条目，并将第三方模型按 claude-opus-5-5、claude-sonnet-5-5、claude-sonnet-4-6 排序，隔离验证通过。最初的增量构建当时尚未安装；随后包含长历史恢复修复的构建已安装在本机。服务目录还列出了 claude-fable-5-1，但当前账号组的 Responses 和 Chat Completions 请求均返回 404，因此未把它加入菜单。新增模型的 200000 上下文长度是保守配置值，服务未在模型目录中提供确切上限。

后续对同一服务列出的 31 个模型名称做定向检查：Anthropic 官方 Claude API 使用 `claude-opus-5-5` 作为 Opus 5.5 的 ID；服务也列出 `claude-opus-5.5`，但一次错误响应将这个带点名称归一化为连字符名称。两个名称的简单问答和自动函数调用均成功，带点名称没有显示出更好的实际能力。`claude-opus-5-5` 通过本机适配器完成了函数调用，也能直接分析一份可读交接；然而在一个旧的超长 Codex 会话里曾输出无关的网页搜索式文本，且大段当前指令的直接请求出现空正文或超时。服务目录和响应中的模型名称只是服务方声明，不能据此证明底层权重身份。对第三方模型，建议在新会话提供简短可读交接；长会话切换应单独验证回答和工具调用。官方 ID 参考：https://platform.claude.com/docs/en/models/opus-5-5/overview 。

安装器曾在 Windows 的 Provider 缺省值为 null 时失败；派生版处理了这个边界。安装前必须正常退出 Codex，随后安装已验证的构建目录；运行中的桌面进程会阻止安装。保留构建目录以供恢复。

## 升级与恢复

### 超长会话切换模型时的 409

若 Codex 在官方模型下经历多次压缩，切到第三方模型时，旧版适配器会从本地会话起点重建加密压缩片段之前的全部可读记录。一个实际会话文件接近 877 MiB，在累计可读内容超过 64 MiB 后被适配器主动拒绝，返回 “The readable history exceeds the recovery size limit”。这不是第三方服务的 409，也没有向官方 GPT 发起恢复请求。

修复后的适配器在该特定容量限制下，若加密片段之后已经有足够的可读交接和新的用户请求，就保留后续可读内容，以明确提示替代不可解密的旧片段；不会把提示缓存成真正的历史摘要，也不会改写原始聊天。没有可读交接、历史文件缺失或记录损坏时仍拒绝恢复。对需要完整旧上下文的任务，应由用户提供可读交接或继续使用原官方模型。更新运行中的适配器需要正常退出 Codex，再安装通过验证的新构建。

### 重启后旧会话长时间“正在思考”，最终收到服务商 HTTP 400

Windows 安装版会通过登录计划任务自动启动本地适配器，无需另开终端常驻运行。排查时先确认计划任务为 Running、适配器 `/health` 返回匹配的 identity、模型密钥所在的用户环境变量存在；这些都正常，也仍可能在某个旧会话失败。

一次官方 GPT 长会话切到第三方 Opus 后，用户看到长时间“正在思考”。服务商账单显示，最终报错前有多笔 `Low`、数十万输入 token 的历史摘要请求；适配器的历史恢复记录随后显示完成。最终会话请求却得到服务商 HTTP 400，桌面端只显示 `upstream_http_400: The model service rejected the request`。这是两段不同的请求：历史摘要已经消耗 token，不能把最终 400 误当成整个过程没有请求或没有费用。当前适配器没有保留上游 400 的具体校验正文，不能据此断定是上下文、工具格式还是其他字段被拒绝。

同一环境下，Opus 的短请求、`xhigh` 加 `max_output_tokens=128000` 的短请求，以及携带约 26 KB 可读交接文档的独立请求均正常完成。这排除了“重启后适配器没启动”“密钥完全失效”和“模型一律不可用”，但不能证明旧会话的完整请求可用。遇到此类失败，不要反复重试昂贵的旧历史恢复；在新会话中选同一模型，提供已有的简短交接 Markdown 和当前任务，先做小请求，再推进长任务。保留原会话供核对。一次针对更新后客户端的隔离兼容测试通过；不能把更新本身认定为这次 400 的原因，也无需仅因版本号变化就停用已安装的适配器。

### 超长会话中 Opus 的 `max_output_tokens`

完整的归因、边界测试和配置步骤见[第三方模型输出额度](OUTPUT_BUDGET.md)。

一次蓝图文档任务在约 35 万输入 token、`xhigh` 推理强度下，第三方 Responses 路由多次恰好用满 8,192 输出 token，Codex 报 `Incomplete response returned, reason: max_output_tokens`。后台计费记录与本地会话计数一致；失败前只有只读环境检查，没有写文件工具调用。模型目录中的 100 万 `context_window` 和 90 万自动压缩阈值是输入侧设置，不能提高单次响应的输出预算。切换较贵的服务分组也不会自动改变这一预算。

用同版本 Codex CLI 的本机临时接收端检查发现：新会话的 `xhigh` Responses 请求省略了 `max_output_tokens`；接收端只读取模型、推理强度和输出额度字段，没有把请求转发到服务商。运行中的适配器对普通请求也没有填入该字段。因此 8,192 不是本地目录或适配器对普通请求设定的额度，而是该第三方路由在未明确指定额度时表现出的有效默认值。由于原失败会话有活跃写入者，尚未捕获那两笔请求的原始请求体，不能据此断言网关的具体实现。适配器另有仅供旧历史摘要使用的 8,192 上限；摘要使用 `low`，与后台 `xhigh` 记录不同。

适配器支持在第三方路由中配置 `default_max_output_tokens`，只在客户端省略该字段时补入；客户端明确指定的额度保持不变。将它写在私有 `connections.json` 对应模型的 `model_specs` 中，构建器会带入路由配置；`examples/connections.example.json` 给出了无密钥示例。例如给支持较长输出的路由设为 `32768`，并用一条短请求验证服务商接受该数值。此设置只控制单次请求的预算，不保证模型会在预算内完成，也不改变官方模型。长会话仍应提供简短可读交接，避免在 `xhigh` 下反复读取全部旧历史和耗尽昂贵的输出预算。

另一次针对 `claude-opus-5-5` 的 `xhigh` 短请求边界测试中，兼容网关接受 `128000` 并正常完成，拒绝 `128001`，错误明确写出最多允许 128000 输出 token。[Anthropic 官方模型规格](https://platform.claude.com/docs/en/models/opus-5-5/overview)标称最大输出为 128K；网关使用十进制数值 128000。这个测试确认了请求参数的可接受上界，没有让模型实际生成接近 128000 token，不能证明网关在长输出时不会另行截断。额度是预算而非目标输出量，设到最大值会提高失控生成时的潜在费用。

本仓库不发布更新清单，也不配置自动更新通道。不要打开 monitor 自动更新。桌面端升级不会仅因版本号变化而停用现有适配器；运行状态、菜单与短请求正常时可继续使用。`patch.py status` 会发现当前已签名的 Windows Store 安装包，并同时报告构建时与当前的客户端版本。若协议不兼容、模型目录需刷新或要安装新构建，再以当前已签名客户端重新构建和隔离验证；安装前正常退出 Codex。Windows 安装版的登录计划任务会在用户登录后启动适配器，用户级环境变量中的 Key 会被读取，不需要开机后手动运行程序。若需撤销，退出 Codex 后运行 python patch.py restore <build-directory>。

## 公开仓库边界

此仓库只放通用源代码、无密钥示例和验证结论。本机用户配置、凭据、连接文件、构建目录、安装包以及真实接口地址均不属于可发布材料。AGENTS.md 的 subagent 调度和模型菜单接入属于不同机制，可以独立配置。
